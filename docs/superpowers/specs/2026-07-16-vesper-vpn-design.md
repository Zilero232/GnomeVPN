# GnomeVPN — VPN-сервис. Дизайн-документ

> Статус: черновик на ревью. Дата: 2026-07-16.
> Рабочее название продукта: **GnomeVPN**. Пакеты монорепо: `@gnomevpn/*`.

## 1. Что это

Кроссплатформенный VPN-сервис с подпиской ~100₽/мес и выбором страны (Россия,
Нидерланды, Германия и др., 5–6 стран на старте). Пользователь выбирает страну и
жмёт одну кнопку **Connect** — приложение поднимает WireGuard-туннель до сервера
выбранной страны; при отключении/окончании подписки туннель гасится, а пир на
сервере снимается.

Технологический стек полностью повторяет проект **Chatovo**:

- **Клиент/лендинг**: Next.js 16 / React 19, архитектура FSD.
- **Desktop-обёртка**: Tauri 2 (Rust). Здесь же живёт VPN-движок.
- **Backend (control plane)**: NestJS на Bun + Prisma + self-hosted Postgres,
  аутентификация через better-auth.
- **Общие типы**: Zod-схемы в `packages/schemas` (`@gnomevpn/schemas`).
- **VPN-серверы**: WireGuard через **wg-easy** (docker), по одному VPS на страну.

### Ключевые решения (зафиксированы на брейншторме)

| Вопрос | Решение |
| --- | --- |
| Платформы | Цель — кроссплатформа. **Реализация начинается с desktop** (Win/macOS/Linux). Mobile (Android → iOS) — отдельный будущий этап. |
| VPN-протокол | **WireGuard**, серверы на **wg-easy**. Обфускация (AmneziaWG) — будущий этап под РФ-DPI. |
| Генерация конфига | **Динамически по нажатию Connect**. При Disconnect / окончании подписки пир снимается. |
| Оплата | **Российский эквайринг (ЮKassa)**, рекуррентные платежи, факт оплаты — через вебхук. |
| Туннель на клиенте | **Встроенный userspace-WireGuard** (`boringtun` в Rust-слое Tauri) — UX «одна кнопка», без сторонних установок. |
| Лимит устройств | **1 активное подключение** на подписку (новый Connect гасит предыдущее). |
| Web-версия VPN | **Нет** (туннель в браузере невозможен). Есть только лендинг + личный кабинет в вебе. |

### Что вне рамок (не реализуем кодом)

- Юридическая часть: ИП/самозанятость, оферта, политика приватности, отсутствие
  логирования трафика. Обязательное **предусловие запуска**, но не задача кода.
- Обфускация трафика (AmneziaWG) — будущий этап.
- Mobile-туннель (Android `VpnService`, iOS `NetworkExtension`) — будущий этап.

## 2. Приоритет качества

Явное требование заказчика: **приоритет — правильная логика и корректный код,
сроки вторичны.** Отсюда: userspace-туннель ради идеального UX, привилегированный
хелпер ради «одной кнопки», минимальный набор тестов на критичную логику,
E2E-проверка реального туннеля как критерий готовности.

## 3. Архитектура: три плоскости

Система строго делится на три независимые плоскости. Это ключевой
архитектурный принцип.

- **Data plane** (трафик пользователя): устройство ⟷ wg-easy на VPS напрямую.
  Backend **не** участвует в потоке трафика — только раздаёт ключи. Важно для
  скорости и приватности.
- **Control plane** (управление): клиент (`/app` в Tauri и `/account` в вебе)
  ⟷ backend по HTTPS (REST + better-auth сессия). Connect/Disconnect, список
  стран, статус подписки, оплата.
- **Provisioning** (выдача пиров): backend ⟷ wg-easy REST API каждого узла по
  приватной сети/туннелю. **Клиент никогда не ходит в wg-easy напрямую** — только
  через backend, чтобы нельзя было получить конфиг без активной подписки.

Жёсткий инвариант: клиент не знает адресов wg-easy-панелей и не имеет к ним
доступа. Он просит у backend «туннель в страну X» и получает готовый
`TunnelConfig`. Управление пирами — исключительно серверное.

## 4. Структура монорепозитория

Bun-workspaces, как в Chatovo.

```text
apps/
├── client/     # Next.js 16 / React 19, FSD.
│               #   /            — лендинг (веб)
│               #   /account     — личный кабинет + оплата ЮKassa (веб)
│               #   /app         — VPN-экран (страны + Connect); только это грузит Tauri
├── tauri/      # Rust-обёртка + VPN-движок (boringtun) + команды vpn_connect/disconnect/status
└── server/     # NestJS на Bun — control plane: auth, subscription, billing, nodes, tunnel
packages/
└── schemas/    # Zod-схемы (@gnomevpn/schemas): TunnelConfig, Node, SubscriptionStatus, DTO
infra/
├── wg-easy/    # docker-compose шаблон одного странового узла (wg-easy)
└── control/    # docker-compose для backend + Postgres
docs/
└── superpowers/specs/   # этот документ и последующие
```

### Разделение веб / app

Один Next.js обслуживает три зоны маршрутов, гейтинг через `isTauri()`
(как в Chatovo):

- `/` — **лендинг** (только веб): витрина, тарифы, «Скачать для …», ссылка в кабинет.
- `/account` — **личный кабинет** (только веб): регистрация/вход, статус подписки,
  **оплата ЮKassa прямо в браузере** (редирект/виджет + возврат), отмена автопродления.
- `/app` — **VPN-приложение**: экран стран + Connect + статус + read-only состояние
  подписки. **Только эту зону грузит Tauri** (`devUrl`/сборка указывают на `/app`).

Мотивация: платёжный флоу (3-D Secure, банковские редиректы) живёт в обычном
браузере, где «просто работает», и не тащится внутрь desktop-приложения. Desktop
остаётся тонким. Приложению нужно лишь читать статус подписки у backend по сессии
(тот же better-auth-логин работает и в приложении).

## 5. Серверная инфраструктура (страновые узлы)

**Один узел = одна страна = один VPS с wg-easy.** Добавить страну = поднять ещё
один VPS по шаблону и добавить строку в таблицу `Node`. Изменений в коде не требуется.

На каждом VPS:

- `wg-easy` (docker): WireGuard-сервер + REST API + веб-панель. **API-порт и панель
  закрыты от интернета** (firewall / слушают только приватный интерфейс). Наружу
  открыт только UDP-порт WireGuard (напр. 51820) — туда идёт трафик пользователей.
- Backend ходит в wg-easy API **не** через публичный интернет: приватная сеть
  между control-VPS и узлами либо зашифрованный туннель. REST wg-easy наружу не торчит.

Операционные требования:

- **DNS через туннель** (в конфиге пира) — защита от DNS-leak.
- **Health-check узла** перед выдачей пира — не выдавать конфиг с мёртвого узла.
- **Сборка мусора висячих пиров**: если клиент отвалился, не нажав Disconnect
  (закрыл ноут), пир повисает. Фоновая задача снимает пиры без свежего хендшейка
  (wg-easy отдаёт `latestHandshake`).

Риск (РФ-аудитория): чистый WireGuard часто режется DPI в РФ (узел в РФ, к
которому подключаются извне, и заграничные узлы, к которым подключаются из РФ).
Лечится на будущем этапе миграцией узлов на **AmneziaWG** (DPI-стойкий,
конфиг почти идентичен). Архитектуру backend/клиента это не ломает — меняются
только поля конфига. **На MVP используем только wg-easy.**

## 6. Backend (control plane)

NestJS на Bun + Prisma + Postgres + better-auth. Модули по конвенции Chatovo
(`module + controller + service + dto`).

### Модули

- **`auth`** — better-auth (email+пароль на старте). Сессия работает и в вебе
  (`/account`), и в desktop-приложении (`/app`).
- **`subscription`** — состояние доступа. Отвечает на единственный вопрос наружу:
  «есть ли у юзера сейчас право подключаться?» → `active && currentPeriodEnd > now`.
- **`billing`** — интеграция ЮKassa:
  - Создание первого платежа 100₽ с `save_payment_method: true` (получаем токен
    для автосписаний).
  - **Вебхук `payment.succeeded`** → продлеваем `currentPeriodEnd` на месяц,
    `status=active`, сохраняем `payment_method_id`. **Единственный доверенный
    источник факта оплаты** (не браузерный редирект!).
  - Рекуррент: фоновая задача берёт активные подписки с истекающим сроком и делает
    автосписание по сохранённому токену. Не прошло → `status=expired`.
  - **Идемпотентность вебхука** (по `yookassaPaymentId`) + проверка подлинности запроса.
- **`nodes`** — реестр стран. `GET /nodes` → список доступных
  (`enabled && healthy`) стран, только публичные поля (страна, флаг, город) —
  без адресов панелей.
- **`tunnel`** — оркестратор (ядро, см. §7). `POST /tunnel/connect { nodeId }`,
  `POST /tunnel/disconnect`.

### Гейт доступа

Единственная дверь между деньгами и VPN — guard на `POST /tunnel/connect`,
который первым спрашивает `subscription`: право есть? Нет → `402 Payment Required`,
клиент показывает «оформи подписку» со ссылкой в веб-кабинет.

### Безопасность backend

- Секреты wg-easy (`wgEasyApiKey`) и ЮKassa — в env/секрет-хранилище, не в коде и
  не в открытом виде в БД (в `Node` — только ссылка на секрет).
- Вебхук ЮKassa — проверка подлинности + идемпотентность по `yookassaPaymentId`.
- Rate-limit на `connect`/`disconnect` (анти-спам созданием пиров).

### Общие схемы

`packages/schemas` (`@gnomevpn/schemas`), общие client↔server: `Node` (публичная
форма), `TunnelConfig`, `SubscriptionStatus`, DTO connect/disconnect. Источник
правды по типам — схемы, типы через `z.infer`.

## 7. Ядро: оркестратор пиров + VPN-движок

### 7A. Оркестратор `POST /tunnel/connect` (backend)

Строгая последовательность, каждый шаг с обработкой ошибки:

1. **Auth-guard** → есть сессия? Нет → `401`.
2. **Subscription-guard** → `active && currentPeriodEnd > now`? Нет → `402`.
3. **Валидация `nodeId`** (Zod) → узел существует, `enabled`, прошёл health-check?
   Нет → `409/503`.
4. **Инвариант «одно подключение»** → если у юзера есть активный `ActivePeer`,
   **сначала снимаем старый** (через wg-easy `DELETE` на его узле), затем создаём
   новый. Это и есть «новый Connect гасит предыдущее».
5. **Создание пира** через wg-easy REST на выбранном узле → приватный ключ клиента,
   адрес в подсети, публичный ключ сервера, endpoint, DNS.
6. **Запись `ActivePeer`** в БД: `userId`, `nodeId`, `wgEasyClientId`, `assignedIp`,
   `createdAt`. Нужна для снятия и сборки мусора.
7. **Ответ** — `TunnelConfig` (Zod): `privateKey`, `address`, `dns`,
   `serverPublicKey`, `endpoint`, `allowedIps` (`0.0.0.0/0, ::/0`),
   `persistentKeepalive`. Приватный ключ существует только в этом ответе и в
   памяти клиента — **в БД не хранится** (wg-easy держит лишь публичный ключ пира).

`POST /tunnel/disconnect`: найти `ActivePeer` → `DELETE` на wg-easy → удалить
`ActivePeer`. Идемпотентно (нет пира → `200`).

**Сборка мусора** (cron): для каждого `ActivePeer` спросить у wg-easy
`latestHandshake`; нет хендшейка дольше N минут → снять пир.

### 7B. VPN-движок в клиенте (Rust-слой Tauri)

Три Tauri-команды в `lib.rs` (обязательно в `generate_handler!`; `lib.rs`
держит логику ради будущего mobile):

- `vpn_connect(config: TunnelConfig, on_event: Channel<VpnEvent>)`
- `vpn_disconnect()`
- `vpn_status() -> VpnState`

Состояние — `Mutex<VpnEngineState>` через `.manage()`. Статус (connecting →
handshake → connected, счётчики трафика, ошибки) стримится в UI через **Channel**
(высокочастотные события).

Что делает `vpn_connect` («userspace WireGuard»):

1. Поднять **TUN-интерфейс** (виртуальная сетевая карта): `wintun` (Windows),
   utun (macOS), `tun` (Linux).
2. Инициализировать WireGuard-стейт из конфига крейтом **`boringtun`** (Cloudflare,
   чистый Rust — предпочтительнее `wireguard-go`: без Go-рантайма, живёт прямо в
   нашем Rust-процессе).
3. Настроить **маршрутизацию**: весь трафик (`0.0.0.0/0`) в TUN, плюс
   исключение-маршрут на сам `endpoint` VPS (иначе рекурсия — пакеты к серверу
   пойдут в туннель к самому себе).
4. Прокачивать пакеты между TUN и UDP-сокетом к VPS через boringtun
   (encapsulate/decapsulate).
5. Слать в Channel события: `Handshake`, `Connected`, `BytesUpdate`, `Error`.

**Привилегии (главная сложность desktop):** создание TUN и правка таблицы
маршрутов требуют админ-прав.

- **Windows**: драйвер `wintun.dll` (тот же, что в офиц. WireGuard) + права
  (манифест/UAC).
- **macOS**: utun доступен; правка маршрутов и, возможно,
  SystemExtension/entitlements → нужна подпись приложения.
- **Linux**: `CAP_NET_ADMIN` (setcap) или запуск через polkit.

Целевое решение для UX «одна кнопка»: **отдельный привилегированный хелпер-сервис**
(ставится один раз при инсталляции), UI-процесс общается с ним по локальному IPC —
тогда нет UAC на каждый Connect. Для самого первого MVP допустимо срезать угол
(запрос прав при старте); целевая архитектура — хелпер (отдельный под-этап).

**Kill-switch** (требование, не блокер MVP): при падении туннеля блокировать весь
трафик мимо TUN (firewall-правило), чтобы реальный IP не «протёк». Реализуется в
том же хелпере.

### Итоговый поток Connect

UI зовёт `POST /tunnel/connect` → получает `TunnelConfig` → зовёт Tauri-команду
`vpn_connect(config)` → Rust поднимает boringtun-туннель → Channel гонит статус в
UI → кнопка «Connected», IP сменился.

## 8. UI/UX клиента

Стек интерфейса — как в Chatovo: React 19 + FSD, `@base-ui-components/react`
(примитивы), SCSS-модули, `lucide-react`, `motion`, `sonner`,
`@tanstack/react-query`, `react-hook-form` + Zod, `next-intl`. Ничего не
изобретаем — переиспользуем существующие библиотеки.

### App-зона (`/app`, грузит Tauri)

1. **Главный экран (страны + Connect):**
   - Крупная **кнопка Connect/Disconnect** с явными состояниями: `disconnected`
     («Подключиться») → `connecting` (пульс/спиннер) → `connected` (зелёная,
     «Отключиться» + таймер сессии). Состояние — из Channel `VpnEvent`.
   - **Селектор страны**: список с флагом-эмодзи, названием, опц. пингом. Данные
     из `GET /nodes` (react-query). Смена страны при активном туннеле =
     disconnect + reconnect на новый узел.
   - **Статус-плашка**: текущий IP/страна, переданный трафик (`BytesUpdate`),
     время соединения.
2. **Экран аккаунта/подписки (read-only):** «Подписка активна до …» или «Подписки
   нет» + кнопка, **открывающая веб-кабинет `/account` во внешнем браузере**
   (Tauri `opener`) — оплата там, не внутри app. Логин (better-auth) — здесь же.
3. **Настройки (MVP-минимум):** автозапуск, тумблер kill-switch, язык, выход.

### Веб-зона (`/`, `/account`, только браузер)

- **Лендинг**: hero, «Скачать для Windows/macOS/Linux», список стран, тариф
  100₽/мес, FAQ, оферта. Визуальный стиль прорабатывается на этапе реализации
  (frontend-design).
- **Кабинет `/account`**: вход/регистрация, статус подписки, **оплата ЮKassa**
  (виджет/редирект), история платежей, отмена автопродления.

### Гейтинг веб vs app

Через `isTauri()` (как в Chatovo): одни и те же React-компоненты, но навигация,
«скачать», страница оплаты — только в вебе; VPN-экран — только в Tauri.

### Обработка состояний ошибок (важно для «работает правильно»)

- Нет подписки (`402` на connect) → модалка «Оформить подписку» → кнопка в веб-кабинет.
- Узел недоступен (`503`) → тост «Страна временно недоступна», кнопка остаётся `disconnected`.
- Хелпер/права недоступны (нет TUN) → понятное объяснение + кнопка «Исправить»
  (переустановить хелпер), не сырая ошибка.
- Потеря туннеля на ходу → авто-`disconnected` + (если включён) kill-switch
  блокирует трафик, тост «Соединение разорвано».

## 9. Модель данных (Prisma, Postgres)

Помимо таблиц better-auth (`user`/`session`/`account`/`verification`):

- **`Subscription`** — `userId` (FK, unique), `status`
  (`active`/`expired`/`canceled`), `currentPeriodEnd`, `yookassaPaymentMethodId?`,
  `yookassaCustomerId?`, timestamps.
- **`Payment`** — журнал: `userId`, `yookassaPaymentId` (unique — идемпотентность
  вебхука), `amount`, `status`, `createdAt`.
- **`Node`** — `id`, `country`, `countryCode`, `flagEmoji`, `city?`, `wgEasyUrl`,
  `wgEasyApiKeyRef` (ссылка на секрет, не сам ключ), `publicEndpoint`, `enabled`,
  `sortOrder`, `capacity?`, `lastHealthyAt?`.
- **`ActivePeer`** — `userId` (FK, **unique** — гарантирует инвариант «1 активный
  туннель»), `nodeId`, `wgEasyClientId`, `assignedIp`, `createdAt`,
  `lastHandshakeAt?`. Приватного ключа здесь нет.

Источник типов — Zod-схемы в `packages/schemas`, из них `z.infer` на клиент и сервер.

## 10. Безопасность (сводка требований)

- **Приватный ключ пира** — только в ответе connect и в памяти Rust-движка; в БД
  и логах никогда.
- **wg-easy API** недоступен из интернета (приватная сеть/туннель); ключи API — в
  секретах, в `Node` только ссылка.
- **Вебхук ЮKassa** — проверка подлинности + идемпотентность; факт оплаты только
  отсюда, не из браузерного редиректа.
- **Гейт подписки** — единственная дверь между деньгами и туннелем, на
  `POST /tunnel/connect`.
- **Rate-limit** на `connect`/`disconnect`.
- **Kill-switch** на клиенте (в хелпере) — защита от утечки реального IP при обрыве.
- **DNS через туннель** — защита от DNS-leak.
- **Секреты** (ЮKassa, wg-easy, better-auth) — env/секрет-хранилище, не в репозитории.

## 11. Тестирование

В Chatovo тестов нет, но для VPN корректность критична — минимальный набор:

- **Backend (юнит, с замоканным wg-easy API):** connect создаёт пира и `ActivePeer`;
  повторный connect снимает старый; disconnect идемпотентен; guard подписки отдаёт
  `402`; вебхук идемпотентен.
- **GC:** висячий пир (нет хендшейка) снимается.
- **Rust-движок:** тест инкапсуляции boringtun на локальном wg-пире (handshake до
  тестового узла).
- **E2E вручную (главный критерий готовности MVP):** на реальном desktop Connect →
  `curl ifconfig.me` показывает IP страны → трафик идёт → Disconnect возвращает
  реальный IP → kill-switch блокирует при обрыве.

## 12. Юридические предусловия (не код)

ИП/самозанятость для эквайринга, оферта, политика приватности, отсутствие
логирования трафика. Обязательное предусловие запуска; реализацией не занимаемся.

## 13. Нарезка на реализацию (этапы)

Проект большой (VPN-движок на Rust — самая сложная часть, плюс эквайринг, плюс
инфра). Спека покрывает всё целиком; реализация — отдельными планами. Каждый
этап — свой цикл spec → plan → implementation.

- **Этап 1 (MVP): реально работающий туннель.**
  1 страна (1 wg-easy VPS) + desktop-туннель (boringtun, права при старте —
  без хелпера) + аккаунты (better-auth) + **заглушка подписки** (без реальной
  оплаты). На этом этапе subscription-guard из §7A шаг 2 реализован, но всегда
  разрешает подключение (заглушка возвращает «право есть») — интерфейс guard'а
  на месте, чтобы Этап 2 просто подменил реализацию на реальную проверку ЮKassa,
  без изменения оркестратора. Критерий готовности — E2E из §11: IP реально
  меняется, Disconnect возвращает исходный.
- **Этап 2: оплата.** Интеграция ЮKassa (создание платежа, вебхук, рекуррент),
  реальный гейт подписки вместо заглушки, веб-кабинет `/account`.
- **Этап 3: остальные страны + лендинг.** Ещё wg-easy узлы + записи `Node`;
  публичный лендинг `/`.
- **Этап 4: привилегированный хелпер + kill-switch.** Убрать UAC на каждый
  Connect, kill-switch, автозапуск.
- **Этап 5: mobile.** Android (`VpnService` через Tauri-плагин), затем iOS
  (`NetworkExtension`, отдельный target, Apple Developer).
- **Этап 6 (по необходимости): обфускация.** Миграция узлов на AmneziaWG под
  РФ-DPI.

Первый план (writing-plans) детализирует **Этап 1**.
